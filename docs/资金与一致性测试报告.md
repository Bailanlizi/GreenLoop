# GreenLoop 资金与一致性测试报告

## 目的与范围

验证模拟账户的资金守恒、订单资金链路、请求幂等性、并发余额约束和订单状态机拦截能力。所有测试仅允许连接 `campus_trade_test`，不得连接生产库。

## 指标口径与通过标准

| 指标 | 口径 | 通过标准 |
| --- | --- | --- |
| 资金守恒差额 | `账户可用+冻结−期初余额−成功充值` | `0.00` |
| 订单—资金单据对账一致率 | 无异常支付订单数 / 本窗口支付订单数 | `100%` |
| 幂等成功率 | 仅产生一次记账的重放场景数 / 全部重放场景数 | `100%` |
| 并发超扣次数 | 并发执行后账户余额为负或成功冻结总额大于初始余额的场景数 | `0` |
| 非法状态迁移拦截率 | 被拒绝的非法迁移数 / 尝试的非法迁移数 | `100%` |

## 方法

1. 单元测试使用 Mockito 验证服务层的幂等短路、余额不足和状态机拒绝逻辑；重放次数固定为 10、50、100。
2. 并发集成测试必须在 MySQL 测试库中使用真实事务、行锁与唯一键，分别覆盖“同订单同请求号”及“同账户多订单且总额超余额”。
3. 测试完成后运行 [`finance-reconciliation.sql`](../campus-trade-api/src/test/resources/finance-reconciliation.sql)。R1 的差额应为 0，R2–R6 的异常查询应返回 0 行。

### 口径更正（2026-08-16）

需求原式包含“`+ 成功退款`”。经代码核查，`refundPaidOrder` 调用 `refundFrozen`，仅将买家的冻结余额转回可用余额，账户总额不变；退款并非平台出金。因此当前实现的正确守恒式不应计入退款金额。SQL 会单独输出 `internal_refund_amount` 以供追踪。若后续接入真实渠道退款或余额提现，应增加出金流水，并在守恒式中扣除真实出金金额。
