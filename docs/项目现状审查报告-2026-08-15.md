# GreenLoop 项目现状审查报告

> 审查日期：2026-08-15  
> 范围：代码、文档、Git 状态与本地构建验证。  
> 说明：本报告为只读盘点，不包含阶段三开发或业务代码修改。

## 一、结论摘要

GreenLoop 已完成阶段 0 至阶段 2 的主体工作：从普通二手交易平台演进为具备**订单状态机、商品锁定、模拟充值、支付冻结、退款、结算与账户流水**的交易闭环。

当前最合理的方向不是立即进入阶段三，而是先完成阶段四中的安全、审计与工程化基础建设。核心业务的可靠性基础已经具备，但项目距离“可交付、可维护、可说明工程质量”仍存在明显缺口。

## 二、已完成能力与亮点

### 1. 产品与系统范围

- 后端：Spring Boot + Spring Security + JWT + MyBatis + MySQL + Redis。
- 用户端：Vue 3 + Vite + Pinia + Element Plus。
- 管理端：Vue 3 + Vite + Pinia + Element Plus + ECharts。
- 用户能力：注册登录、商品发布/浏览、订单、钱包、私信、收藏、评价、通知、AI 辅助。
- 管理能力：用户、商品、订单、配送、地点、运营统计，以及账户、支付、退款、结算、流水的查询视图。

### 2. 交易与资金链路已落地

当前实现已经具有较好的业务完整性：

1. 创建订单时，以条件更新锁定可售商品，减少重复下单风险。
2. 新订单进入 `PENDING_PAYMENT`，商品保持 `LOCKED`。
3. 支付接口以 `requestId` 防重复提交；买家可用余额转为冻结余额。
4. 支付后订单进入面交待处理或快递待发货。
5. 取消订单会释放商品，并将冻结资金退回可用余额。
6. 确认完成时，从买家冻结余额扣减并计入卖家可用余额。
7. 充值、支付冻结、退款、结算都写入追加式账户流水，且保存变动前后余额快照。
8. 订单支付超时任务会取消订单、释放商品，避免商品长期被占用。

这部分是项目最有价值的亮点：不仅实现了页面功能，也考虑了幂等、状态机、事务、行锁/版本校验与资金去向追溯。

## 四、问题与优先级

### P0：应立即处理

#### 1. 敏感配置已进入默认配置文件

后端默认配置包含数据库、邮件、JWT 等敏感值。无论仓库是否公开，都应将其视作存在泄露风险。

建议：轮换已有凭据；改用环境变量；新增 `application-example.yml`；在提交检查中加入密钥扫描。

#### 2. CORS 配置过宽

当前 CORS 允许任意来源并允许携带凭据。生产环境下会扩大跨站请求风险。

建议：按开发、测试、生产环境配置明确来源白名单；验证预检请求与 Cookie/Authorization 行为。

### P1：阶段四的主干工作

#### 3. 审计尚未形成完整闭环

现有 `X-Trace-Id` 请求日志和资金流水是良好起点，但缺少持久化、可查询的关键操作审计：后台人工操作、权限变更、账户冻结/解冻、订单强制取消等均需记录操作者、角色、时间、业务单号、变更前后摘要、结果和追踪号。

#### 4. 测试层次不足

目前只有 15 个后端测试，且主要为单元测试。缺少：

- MockMvc 或真实 HTTP 接口集成测试；
- 数据库迁移和 MySQL 集成测试；
- 登录、角色和越权测试；
- 用户端与管理端关键流程测试；
- 持续集成（CI）测试门禁。

#### 5. 交付配置不一致

开发基准写 Java 21，而 Dockerfile 使用 Java 17，并且 Dockerfile 中的 JAR 名称与当前 Maven artifact 不一致。仓库暂无 Docker Compose、数据库迁移工具和 CI 配置。

建议：统一运行时版本；修正镜像构建；增加 Compose、健康检查、初始化/迁移说明和 CI。

### P2：质量与维护性改进

#### 6. 文档与现有代码存在漂移

阶段二已经实现 `PENDING_PAYMENT`、`LOCKED`、账户/支付/退款/结算/流水表，但 README、PRD 和架构文档仍有部分阶段一表述。应把 `开发基准.md` 确立为唯一实现真源，再同步其他文档。

#### 7. 前端首包偏大

两个前端生产构建均提示存在超过 500KB 的 chunk，主包约 1MB。建议后续做路由懒加载、ECharts 与 Element Plus 按需加载、构建体积预算。

#### 8. 仓库卫生不足

已有 84 个上传测试/运行图片被 Git 跟踪，`.gitignore` 仅忽略了 `.workbuddy`。建议忽略 `uploads/`、`dist/`、本地密钥配置；演示资源放入明确管理的样本目录。

## 五、建议的阶段四顺序

1. **安全基线**：密钥轮换、环境变量、CORS 白名单、默认管理员策略、上传边界、鉴权与越权回归测试。
2. **审计与可观测性**：设计审计事件表；统一 traceId；为后台和资金关键操作持久化审计记录；提供管理端检索。
3. **工程化交付**：Flyway/Liquibase、Dockerfile/Compose、一键启动、健康检查、日志规范与 CI。
4. **测试体系**：补充资金、订单、权限、审计的单元测试与集成测试，最后增加关键交易链路端到端测试。
5. **文档与性能**：同步状态机和资金模型文档，处理前端拆包与仓库清理。

## 六、后续讨论建议

下次可直接围绕“阶段四最小可交付版本”确定范围：先选定安全基线、审计模型、迁移/部署方式与测试门禁，再拆分为可逐项验收的开发任务。阶段三风控可以在这些基础稳定后再恢复推进。
