# 开发基准

> 本文档为 GreenLoop 可信交易与资金清结算平台当前代码库的开发基准，也是**接口、数据表、状态枚举与虚拟账户模型的唯一权威真源**。后续新增功能、接口联调、数据库调整、测试验收和答辩说明均以本文档为准。当前实现由校园二手交易场景演进而来，存量工程命名仍保留兼容性。数据库 ER 图与表关系说明集中维护在《系统架构设计文档》，本文档不再重复绘制与复述。

## 一、项目现状

GreenLoop 当前采用前后端分离结构，仓库内包含三个主要工程：

| 工程 | 路径 | 职责 | 默认端口 |
| --- | --- | --- | --- |
| 后端 API | `campus-trade-api` | 提供用户、商品、订单、评价、消息、后台管理、AI 等 REST 接口 | 8080 |
| 用户端 | `campus-trade-web` | 面向普通用户，提供注册登录、商品浏览、发布、下单、私信、个人中心等功能 | 5173 |
| 管理端 | `campus-trade-admin` | 面向管理员，提供用户、商品、订单、配送、交易地点、统计等管理功能 | 8000 |

当前项目不是 RuoYi-Vue-Plus 工程，而是自建 Spring Boot + Vue 工程。旧文档中关于 RuoYi、Sa-Token、MyBatis-Plus、`sys_user`、统一 `/api` 前缀等内容不再作为实现基准。

## 三、统一返回格式

后端统一使用 `Result<T>` 返回：

```json
{
  "code": 200,
  "msg": "操作成功",
  "data": {}
}
```

约定：

| 场景 | 规则 |
| --- | --- |
| 成功 | `Result.success(data)`，`code = 200` |
| 失败 | `Result.error(msg)` 或抛出 `CustomException` |
| 前端判断 | 以 `code === 200` 作为业务成功判断 |
| 错误提示 | 后端返回 `msg`，前端直接展示或转换为用户友好提示 |

新增接口必须保持该结构，不要直接返回裸对象、字符串或不一致的错误格式。

## 四、认证与权限基准

### 1. 登录方式

当前项目使用 Spring Security + JWT：

- 注册接口：`POST /users/register`
- 登录接口：`POST /users/authenticate`
- 登录成功后返回 JWT。
- 前端通过 Axios 在请求头中携带 Token。
- 后端通过 `JwtAuthenticationFilter` 解析 Token。
- 控制器中通过 `@AuthenticationPrincipal AuthenticatedUser user` 获取当前登录用户。

### 2. 放行接口

当前允许未登录访问的接口包括：

### 3. 权限边界

| 场景 | 基准 |
| --- | --- |
| 普通用户操作个人资源 | 必须校验当前登录用户 ID |

### 1. 命名规则

| 层级 | 规则 |
| --- | --- |
| 数据库表名 | 小写，下划线，如 `user_addresses` |
| 数据库字段 | 下划线，如 `credit_score`、`delivery_method` |
| Java 字段 | 小驼峰，如 `creditScore`、`deliveryMethod` |
| JSON 字段 | 小驼峰，和 Java DTO 保持一致 |
| Mapper XML | 开启 `map-underscore-to-camel-case` |

### 2. SQL 变更规则

- 任何新增字段、新增表、枚举值变化都必须同步修改 `campus_trade.sql`（权威建表脚本）。
- 金额字段统一使用 `DECIMAL(18,2)` + `BigDecimal`，禁止浮点类型。
- 不要只改实体类，不改 SQL。
- 不要只改 SQL，不改 Mapper XML。
- 修改字段含义时必须同步更新本文档和前端 API 封装。
- 注意：根目录 `campus_trade_test.sql` 为测试库种子脚本，当前尚未包含资金账户相关表且金额精度仍为 `DECIMAL(10,2)`，与权威脚本存在漂移，禁止用它重建正式库；后续应改为版本化迁移（Flyway/Liquibase）。

## 七、状态枚举基准

### 1. 商品状态

当前 `product.status` 使用：

| 状态 | 含义 |
| --- | --- |
| `AVAILABLE` | 可购买 |
| `SOLD` | 已售出或已被订单占用 |
| `DELISTED` | 已下架 |

说明：

- 当前项目暂不使用 `ON_SALE`、`RESERVED`、`OFF_SHELF`。
- 下单后商品会从 `AVAILABLE` 变为 `SOLD`。
- 取消订单时商品应恢复为 `AVAILABLE`。
- 若后续要区分“已预订”和“已售出”，可新增 `RESERVED`，但必须同步后端、前端、SQL 和文档。

### 2. 订单状态

当前 `orders.order_status` 使用：

| 状态 | 含义 |
| --- | --- |
| `PENDING_PAYMENT` | 已创建订单、待买家支付（支付前商品保持可售） |
| `AWAITING_MEETUP` | 线下面交待处理（支付完成后进入） |
| `AWAITING_SHIPMENT` | 快递订单待发货（支付完成后进入） |
| `SHIPPED` | 已发货 |
| `COMPLETED` | 已完成 |
| `CANCELLED` | 已取消 |

状态流转基准：

| 场景 | 商品状态 | 订单状态 |
| --- | --- | --- |
| 商品发布后 | `AVAILABLE` | 无订单 |
| 创建订单（未支付） | `SOLD` | `PENDING_PAYMENT` |
| 买家支付成功 | `SOLD` | `AWAITING_MEETUP` / `AWAITING_SHIPMENT`（视配送方式） |
| 买家取消可取消订单 | `AVAILABLE` | `CANCELLED` |
| 管理员强制取消订单 | `AVAILABLE` | `CANCELLED` |
| 快递订单发货 | `SOLD` | `SHIPPED` |
| 线下面交完成确认 | `SOLD` | `COMPLETED` |
| 快递订单完成确认 | `SOLD` | `COMPLETED` |

### 3. 配送方式

当前 `orders.delivery_method` 使用：

| 值 | 含义 | 必填字段 |
| --- | --- | --- |
| `MEETUP` | 线下面交 | `meetupLocationId` |
| `SHIPPING` | 快递配送 | `shippingAddressId` |

商品 `delivery_options` 使用字符串保存支持方式，例如：

- `MEETUP`
- `SHIPPING`
- `MEETUP,SHIPPING`

创建订单时必须校验用户选择的配送方式在商品支持范围内。

### 4. 评价与信用分

当前评价表为 `ratings`，一笔订单同一个评价人只能评价一次。

信用分建议统一为：

| 星级 | 信用分变化 |
| --- | --- |
| 5 星 | +3 |
| 4 星 | +1 |
| 3 星 | 0 |
| 2 星 | -1 |
| 1 星 | -3 |

实现基准：

- 只有 `COMPLETED` 订单允许评价。
- 评分必须限制在 1 到 5。
- 评价插入和信用分更新必须在同一个事务内完成。
- 重复评价不能导致信用分重复变化。
- 信用分最低不低于 0。
- 如果最终业务只允许买家评价卖家，则后端必须限制卖家不能反向评价买家。

### 5. 虚拟账户与资金单据状态

阶段二已落地模拟资金体系，核心设计如下：

- **虚拟账户 `account`**：每个用户一个账户，余额拆分为 `available_balance`（可用）与 `frozen_balance`（冻结），通过 `version` 字段做乐观锁防并发超扣。新用户注册自动开户，存量用户惰性开户兜底。
- **资金流水 `account_flow`**：追加式、不可变，每笔变动记录 `availableBefore/After`、`frozenBefore/After` 余额快照，`business_type` 包括 `RECHARGE`、`PAYMENT_FREEZE`、`REFUND`、`SETTLEMENT_OUT`、`SETTLEMENT_IN` 等。
- **单据状态**：
  - 充值单 `recharge_order.status`：待充值 → 成功。
  - 支付单 `payment_order.status`：`PENDING`（待支付）→ `FROZEN`（已冻结资金）→ `SETTLED`（已结算给卖家）/ `REFUNDED`（已退款）。
  - 冻结记录 `account_freeze_record.status`：`FROZEN` → `RELEASED`（结算释放）/ `REFUNDED`（退款释放）。
  - 退款单 `refund_order.status`：待退款 → 已退款。
  - 结算单 `settlement_order.status`：待结算 → 已结算。
- **幂等**：充值与支付均通过 `request_id` + 用户唯一约束防止重复扣款/重复退款；一个订单仅对应一笔支付单（行锁 + 状态条件更新）。
- **资金守恒**：DB 层对流水前后余额加 `CHECK (after >= 0)` 约束；系统总余额应恒等于「总充值 − 总退款」（资金守恒断言为阶段四测试目标）。
- **超时**：`PENDING_PAYMENT` 订单 30 分钟未支付自动关闭，定时任务逐笔加锁、独立事务、状态条件更新防并发冲突。

## 八、核心业务规则

### 1. 用户规则

- 用户名必须唯一。
- 密码必须加密保存。
- 登录成功后使用 JWT 访问受保护接口。
- 普通用户不能手动修改自己的信用分。
- 管理端禁用用户后，用户不应继续访问受保护功能。

### 2. 商品规则

- 发布商品必须登录。
- 商品必须包含标题、价格、分类、封面图等核心字段。
- 商品价格不能小于 0。
- 普通用户只能编辑和修改自己的商品。
- 已下架商品不能下单。
- 已售出或已被订单占用的商品不能重复下单。

### 3. 订单规则

- 买家不能购买自己发布的商品。
- 商品不存在时不能创建订单。
- 商品状态不是 `AVAILABLE` 时不能创建订单。
- 创建订单时保存成交价格，避免商品价格后续变化影响历史订单。
- 下单成功后商品状态变为 `SOLD`。
- 取消订单后商品恢复为 `AVAILABLE`。
- 已完成、已取消订单不能重复取消或重复完成。
- 快递订单只有在 `AWAITING_SHIPMENT` 状态才能发货。
- 线下面交订单不能走快递发货接口。

### 4. 评价规则

- 未完成订单不能评价。
- 非订单相关用户不能评价。
- 同一用户对同一订单不能重复评价。
- 评分必须在 1 到 5。
- 信用分计算规则必须和文档、页面展示、答辩说明一致。

### 5. 消息与通知规则

- 私信发送人和接收人不能相同。
- 消息内容不能为空。
- 订单创建、发货、状态变化等关键事件建议创建通知。
- 通知未读数应与通知列表状态保持一致。

## 十、配置与安全基准

### 1. 本地配置

后端配置文件职责划分（key 零重叠，`application.properties` 优先级高于 `application.yml`）：

```text
campus-trade-api/src/main/resources/application.properties   # 共享配置（受控提交）：server/mybatis/jwt/文件上传/邮件主机/安全默认值，无敏感信息
campus-trade-api/src/main/resources/application.yml          # 本机特有配置（gitignore 忽略，不提交）：数据库账号密码、邮箱授权码、AI key、本地管理员引导
campus-trade-api/src/main/resources/application-test.yml     # 测试 profile 配置（受控提交）：测试库/Redis 库/占位邮箱账号
campus-trade-api/src/main/resources/application_example.yml  # 本地配置模板（受控提交，含占位符，复制为 application.yml 使用）
```

本地运行需要：

- MySQL 8.x
- Redis 6.x+
- JDK 17
- Maven
- Node.js 16+

### 2. 敏感信息规则

- **不要**在任何提交仓库的文件中写入真实数据库密码、邮箱授权码、JWT 密钥、AI Key。受控的 `application.properties` / `application-test.yml` 中不出现任何敏感值（JWT 默认密钥仅用于开发，生产通过 `JWT_SECRET` 环境变量覆盖）。
- 本地运行复制 `application_example.yml` 为 `application.yml` 并填入真实值；该文件已被 `.gitignore` 忽略。
- 也可通过环境变量覆盖（优先级最高）：`SPRING_DATASOURCE_URL`、`SPRING_DATASOURCE_USERNAME`、`SPRING_DATASOURCE_PASSWORD`、`SPRING_REDIS_HOST/PORT/PASSWORD`、`SPRING_MAIL_USERNAME`、`SPRING_MAIL_PASSWORD`、`JWT_SECRET`、`JWT_EXPIRATION`、`AI_ENABLED`、`AI_API_KEY` 等。
- 本地真实配置由个人保存，不作为团队共享文档内容。
- CI 与 Docker Compose 均通过环境变量注入敏感项，不依赖本机 `application.yml`。

> `application_example.yml`（下划线）只是复制模板，并非 Spring Profile 自动加载命名；`application-test.yml` 仅用于测试 profile。Docker Compose 通过根目录 `.env` 向容器注入同类配置（镜像构建时 `.dockerignore` 已排除 `application.yml` / `application.properties`，运行时全部走环境变量）。

环境变量映射（对应环境变量名已内置支持，用于生产/CI/Docker 覆盖）：

- `spring.datasource.password` → `SPRING_DATASOURCE_PASSWORD`
- `spring.redis.password` → `SPRING_REDIS_PASSWORD`
- `spring.mail.username` / `spring.mail.password` → `SPRING_MAIL_USERNAME` / `SPRING_MAIL_PASSWORD`
- `jwt.secret` / `jwt.expiration` → `JWT_SECRET` / `JWT_EXPIRATION`（未设置时使用开发默认值）
- `ai.api-key` → `AI_API_KEY`

### 3. 缓存与分布式任务基准

Redis 既承担 Spring Cache 的热点数据缓存，也承担订单支付超时扫描的分布式协调；两类用途共用同一 Redis 实例/逻辑库时必须保持现有 key 命名空间约定。

| 项 | 当前实现与约束 |
| --- | --- |
| 缓存 key 前缀 | `greenloop:{cacheName}:{key}`；新增缓存不得绕过此前缀。 |
| 缓存 TTL | `products` / `product` 10 分钟，`order` 15 分钟，`recommendations` 30 分钟，`meetup_locations` / `categories` 2 小时；未列出的缓存默认 30 分钟。 |
| 雪崩防护 | 每次缓存写入在基准 TTL 上施加 ±20% 随机抖动；不要在业务代码中自行写死统一过期时间。 |
| 穿透防护 | Spring Cache 允许缓存 `null`；空值 TTL 为基准 TTL 的 1/5，最低 30 秒。真实数据写入或更新时必须按关联缓存执行 `@CacheEvict`。 |
| 序列化 | key 使用字符串序列化，value 使用 `GenericJackson2JsonRedisSerializer`；业务侧不新增自定义 `RedisTemplate<String, Object>`。 |
| 过期订单扫描 | `OrderExpirationScheduler` 每 `orders.payment-expiration-scan-ms`（默认 60 秒）扫描一批最多 100 笔待支付超时订单。 |
| 多实例互斥 | 扫描前以 `greenloop:lock:order-expiration-scan` 尝试获取 Redisson 锁；未抢到锁的实例立即跳过，不得改成阻塞等待。锁不显式设置租期，由 watch dog 自动续期；持锁实例异常后默认约 30 秒可被其他实例接管。 |

新增或变更缓存时，必须同时检查查询缓存和所有写路径的失效范围；新增定时任务时，若任务会修改共享业务数据，应评估是否需要采用同类分布式互斥。

### 4. 通知与异步投递基准

- 系统通知与私信未读数独立统计；通知列表支持分页和 `ALL` / `UNREAD` 筛选，单条已读更新必须同时按通知 ID 和当前用户 ID 限定。
- 通知关联对象通过 `related_type` 区分 `ORDER` 和 `PRODUCT`；订单事件跳转订单列表，求购匹配跳转商品详情。
- `notifications.async-enabled=false` 为默认模式，通知随业务事务写入。开启异步模式前，必须先执行 `scripts/migrate_notification_outbox.sql` 并部署 RabbitMQ。
- 异步模式下业务事务只写 `outbox_event`；发布器重试三次，失败事件状态为 `DEAD`。消费者以 `source_event_id` 唯一约束去重；管理员可通过 `/admin/notifications/outbox/{id}/replay` 重放死信事件。

## 十一、前端开发基准

### 1. API 封装

- 用户端接口统一放在 `campus-trade-web/src/api`。
- 管理端接口统一放在 `campus-trade-admin/src/api`。
- 页面组件不要直接写重复 Axios 配置。
- 用户端 `apiClient` 的 `baseURL` 固定为 `/api`；API 封装函数只能传入不带 `/api` 的内部路径。
- 接口路径变化必须同步 API 封装和页面调用。

### 2. 登录状态

- 登录后保存 Token 和用户信息。
- 访问需要登录的页面时应做路由拦截。
- 接口返回未登录或 Token 失效时，应清理登录态并跳转登录页。

### 3. 页面交互

- 表单提交前做基础校验。
- 异步请求应有加载状态。
- 空列表应显示空状态。
- 后端业务错误应通过 `msg` 给用户明确提示。
- 订单、商品、评价等状态按钮必须根据当前状态禁用或隐藏。
