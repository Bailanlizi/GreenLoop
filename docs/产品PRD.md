# GreenLoop 可信交易平台 PRD

## 一、项目概况

### 1.1 项目名称

GreenLoop 可信交易平台

### 1.2 产品定位

GreenLoop 是一款面向个人、组织与园区场景的可信闲置资产交易平台，采用前后端分离架构，为用户提供商品发布、商品浏览、搜索筛选、在线沟通、下单交易、配送管理、评价反馈、信用分展示和后台运营管理等能力。

平台围绕“闲置资产可信流转”的实际需求，提供结构化、可检索、可追踪的交易方式，并将逐步补齐模拟支付、资金托管、账户流水、退款结算、风险控制和审计能力。

### 1.3 当前项目形态

| 模块 | 路径 | 说明 |
| --- | --- | --- |
| 后端 API | `campus-trade-api` | 提供用户、商品、订单、评价、消息、收藏、通知、求购、管理端、AI 等接口 |
| 用户端 | `campus-trade-web` | 普通用户使用，完成注册登录、浏览商品、发布商品、下单、消息、个人中心等功能 |
| 管理端 | `campus-trade-admin` | 管理员使用，完成用户、商品、订单、配送、交易地点、统计等管理功能 |

### 1.4 目标用户

| 用户 | 需求 |
| --- | --- |
| 买家 | 搜索低价二手商品，查看商品详情，与卖家沟通并下单 |
| 卖家 | 发布闲置商品，处理订单，完成交易并积累信用 |
| 管理员 | 管理平台用户、商品、订单、配送和基础运营数据 |

### 1.5 核心痛点

闲置资产交易常见问题包括：

- 商品信息分散，历史消息容易被覆盖。
- 商品分类和描述不统一，搜索效率低。
- 买卖双方缺少基础信用信息。
- 交易过程缺少标准订单记录。
- 商品可能被多人重复购买。
- 沟通记录分散，不方便回看。
- 管理者缺少统一后台进行用户、商品和订单管理。

### 1.6 产品解决方案

GreenLoop 通过以下方式解决上述问题：

- 建立统一商品展示和搜索平台。
- 使用标准化商品字段，包括分类、价格、成色、图片和配送方式。
- 提供用户注册、登录和个人资料管理。
- 提供站内私信、通知、收藏和求购功能。
- 建立订单流程，记录交易关系和交易状态。
- 支持线下面交和快递配送两种方式。
- 通过评价和信用分体现用户交易表现。
- 提供管理后台进行用户、商品、订单、配送和数据统计管理。
- 引入 AI 能力辅助商品发布、价格建议、语义搜索和推荐。

## 二、产品目标

### 2.1 MVP 目标

当前项目 MVP 重点保证一条可演示、可追踪的交易流程：

```text
用户注册登录
-> 浏览和搜索商品
-> 发布商品
-> 私信沟通
-> 提交订单
-> 根据配送方式进入线下面交或快递配送流程
-> 订单完成
-> 用户评价
-> 信用分更新
-> 管理端查看和管理交易数据
```

### 2.2 当前功能边界

当前项目支持：

- 用户注册、登录、JWT 鉴权。
- 商品发布、编辑、下架、搜索、筛选、详情查看。
- 商品图片上传和访问。
- 商品收藏。
- 商品求购。
- 站内私信。
- 系统通知。
- 订单创建、订单查询、订单状态更新。
- 线下面交和快递配送。
- 收货地址管理。
- 线下交易地点管理。
- 订单评价和用户信用分。
- 管理端用户、商品、订单、配送、统计管理。
- AI 发布建议、价格建议、语义搜索和推荐能力。

当前项目不重点支持：

- 真实在线支付。
- 退款和售后。
- 第三方物流实时追踪。
- 真实教务系统认证。
- 投诉、举报和申诉流程。
- 平台抽佣。
- 多学校运营后台。

## 四、核心功能需求

### 4.1 用户注册与登录

#### 功能说明

用户可以注册 GreenLoop 账号并登录系统。登录成功后，系统返回 JWT，用于后续访问受保护接口。

#### 当前接口

| 功能 | 接口 |
| --- | --- |
| 注册 | `POST /users/register` |
| 登录 | `POST /users/authenticate` |
| 用户公开资料 | `GET /users/{id}/profile` |
| 更新个人资料 | `PUT /api/me/profile` |

#### 基本规则

- 用户名不能重复。
- 密码需要加密保存。
- 登录后通过 JWT 访问受保护接口。
- 未登录用户不能发布商品、收藏商品、发送消息或创建订单。

### 4.2 商品分类

#### 功能说明

平台提供固定商品分类，便于用户发布商品和浏览筛选。

#### 当前分类表

分类数据由 `category` 表维护，当前默认分类包括：

- 教材书籍
- 电子产品
- 生活用品
- 代步工具
- 服饰鞋包
- 文具用品
- 其他杂项

#### 当前接口

| 功能 | 接口 |
| --- | --- |
| 分类列表 | `GET /categories` |
| 清理分类缓存 | `POST /categories/clear-cache` |

### 4.3 商品发布与管理

#### 功能说明

登录用户可以发布二手商品，并在“我的商品”中查看和管理自己发布的商品。

#### 商品主要字段

| 字段 | 说明 |
| --- | --- |
| `id` | 商品 ID |
| `sellerId` | 卖家 ID |
| `categoryId` | 分类 ID |
| `title` | 商品标题 |
| `description` | 商品描述 |
| `price` | 售价 |
| `conditionLevel` | 成色等级 |
| `coverImage` | 封面图 |
| `status` | 商品状态 |
| `deliveryOptions` | 支持的配送方式 |
| `createTime` | 发布时间 |
| `updateTime` | 更新时间 |

#### 当前商品状态

| 状态 | 含义 |
| --- | --- |
| `AVAILABLE` | 可购买 |
| `SOLD` | 已售出或已被订单占用 |
| `DELISTED` | 已下架 |

说明：当前项目未单独使用“已预订”状态。下单后商品直接变为 `SOLD`，取消订单后恢复为 `AVAILABLE`。

#### 当前接口

| 功能 | 接口 |
| --- | --- |
| 商品列表 | `GET /products` |
| 商品详情 | `GET /products/{id}` |
| 发布商品 | `POST /products` |
| 编辑商品 | `PUT /products/{id}` |
| 修改商品状态 | `PUT /products/{id}/status` |
| 我的商品 | `GET /products/my` |
| 商品风险检测 | `POST /products/risk-check` |
| 相似商品推荐 | `GET /products/{id}/recommendations` |

#### 基本规则

- 发布商品必须登录。
- 商品标题不能为空。
- 商品价格不能小于 0。
- 商品应包含封面图。
- 用户只能编辑和管理自己的商品。
- 已下架、已售出或已被订单占用的商品不能下单。

### 4.12 订单交易流程

#### 功能说明

当前项目不接入真实支付，订单用于记录交易关系、锁定商品、管理配送和确认交易完成。

#### 当前订单状态

| 状态 | 含义 |
| --- | --- |
| `AWAITING_MEETUP` | 线下面交待处理 |
| `AWAITING_SHIPMENT` | 快递订单待发货 |
| `SHIPPED` | 已发货 |
| `COMPLETED` | 已完成 |
| `CANCELLED` | 已取消 |

#### 配送方式

| 方式 | 含义 | 订单初始状态 |
| --- | --- | --- |
| `MEETUP` | 线下面交 | `AWAITING_MEETUP` |
| `SHIPPING` | 快递配送 | `AWAITING_SHIPMENT` |

#### 当前接口

| 功能 | 接口 |
| --- | --- |
| 创建订单 | `POST /orders` |
| 订单详情 | `GET /orders/{orderId}` |
| 我的购买 | `GET /orders/my-purchases` |
| 我的出售 | `GET /orders/my-sales` |
| 更新订单状态 | `PUT /orders/{orderId}/status` |

#### 订单创建规则

- 用户必须登录。
- 商品必须存在。
- 商品状态必须为 `AVAILABLE`。
- 用户不能购买自己发布的商品。
- 商品必须支持所选配送方式。
- 线下面交必须选择交易地点。
- 快递配送必须选择收货地址。
- 订单创建成功后保存成交价格。
- 订单创建成功后商品状态变为 `SOLD`，防止重复下单。

#### 状态流转

| 场景 | 商品状态 | 订单状态 |
| --- | --- | --- |
| 商品发布后 | `AVAILABLE` | 无订单 |
| 线下面交下单 | `SOLD` | `AWAITING_MEETUP` |
| 快递配送下单 | `SOLD` | `AWAITING_SHIPMENT` |
| 买家取消订单 | `AVAILABLE` | `CANCELLED` |
| 管理员取消订单 | `AVAILABLE` | `CANCELLED` |
| 快递订单发货 | `SOLD` | `SHIPPED` |
| 订单完成 | `SOLD` | `COMPLETED` |

### 4.14 评价与信用分

#### 功能说明

订单完成后，订单相关用户可以提交评价。评价记录保存到 `ratings` 表，并影响被评价用户的信用分。

#### 当前接口

| 功能 | 接口 |
| --- | --- |
| 提交评价 | `POST /api/orders/{orderId}/ratings` |
| 用户评价列表 | `GET /api/users/{userId}/ratings` |

#### 评价规则

- 只有 `COMPLETED` 订单可以评价。
- 评价人必须是订单相关用户。
- 同一用户对同一订单只能评价一次。
- 评分应限制在 1 到 5。
- 评价保存后更新被评价用户信用分。

#### 信用分规则

当前代码实现规则为：

| 星级 | 信用分变化 |
| --- | --- |
| 5 星 | +1 |
| 4 星 | +1 |
| 3 星 | 0 |
| 2 星 | -2 |
| 1 星 | -2 |

说明：当前后端在 `RatingServiceImpl.submitRating` 中按评分区间更新信用分，`score >= 4` 视为好评并为被评价用户增加 1 分，`score <= 2` 视为差评并减少 2 分，3 星不改变信用分。同一订单同一评价人只能评价一次，因此重复评价不会重复影响信用分。

## 八、业务规则

### 8.1 用户规则

- 用户必须登录后才能发布商品、收藏商品、发送消息和创建订单。
- 用户名不能重复。
- 密码必须加密保存。
- 管理端可以禁用用户。
- 用户信用分由系统根据评价规则更新，普通用户不能手动修改。

### 8.2 商品规则

- 商品刚发布时默认可购买。
- 商品下单后变为 `SOLD`。
- 已售出、已下架或已被订单占用的商品不能再次下单。
- 订单取消后商品恢复为 `AVAILABLE`。
- 卖家只能编辑自己的商品。

### 8.3 订单规则

- 每笔订单关联一个商品。
- 每笔订单包含一个买家和一个卖家。
- 买家不能购买自己的商品。
- 商品状态不是 `AVAILABLE` 时不能下单。
- 下单时保存成交价格。
- 不同配送方式需要校验不同字段。
- 当前 MVP 不接入真实支付，因此不设置已支付、退款等状态。

### 8.4 评价与信用规则

- 只有已完成订单可以评价。
- 同一订单同一评价人只能评价一次。
- 评分范围为 1 到 5。
- 评价后更新被评价用户信用分。
- 当前实现中，4 星和 5 星增加 1 分，1 星和 2 星扣减 2 分，3 星不改变信用分。
- 重复提交不能重复修改信用分。

### 8.5 管理端规则

- 管理端仅允许管理员访问。
- 管理员可以管理用户、商品、订单、配送和交易地点。
- 管理端修改订单时也应保证商品状态和订单状态一致。

## 十一、当前实现与原始 PRD 的主要调整

| 原始设想 | 当前项目实际情况 | 调整说明 |
| --- | --- | --- |
| 手机号验证码注册 | 当前以用户名、密码、邮箱相关能力为主 | 以当前用户接口为准 |
| 校园认证作为交易前置条件 | 当前项目重点是注册登录和个人资料，未完整落地真实校园认证 | 不再强制写为当前 MVP 必备闭环 |
| 商品状态包含“在售、已预订、已售出、已下架” | 当前使用 `AVAILABLE`、`SOLD`、`DELISTED` | 下单后直接进入 `SOLD` |
| 订单状态为待确认、待取货、已完成、已取消 | 当前使用 `AWAITING_MEETUP`、`AWAITING_SHIPMENT`、`SHIPPED`、`COMPLETED`、`CANCELLED` | 增加快递配送流程 |
| 卖家确认订单和取货码验证 | 当前重点为线下面交/快递配送和订单状态更新 | 取货码不作为当前已落地功能 |
| 评价只保存星级 | 当前 `ratings` 表支持评分和文字评价 | 以当前评价表为准 |
| 收藏、求购、通知、AI 为后续功能 | 当前项目已有相关实现 | 纳入当前 PRD |
| 后台运营数据分析不纳入 MVP | 当前已有管理端仪表盘和统计接口 | 纳入管理端需求 |

## 十二、项目总结

当前 GreenLoop 已从最初的校园二手交易 MVP 设想，扩展为包含用户端、管理端和后端 API 的完整前后端分离项目。相比原始 PRD，当前项目在订单配送、管理后台、收藏、通知、求购和 AI 能力上都有所扩展，同时也有部分原始设想没有完全落地，例如真实校园认证、取货码流程和独立“已预订”状态。

因此，新版 PRD 以当前代码库实际功能为准，重点描述已经具备或应继续稳定完善的能力。后续开发应围绕交易主流程继续加强状态一致性、异常处理、信用分规则统一和演示稳定性，保证项目能够完整展示校园二手交易从商品发布到订单完成再到评价反馈的核心价值。
