# GreenLoop 开发目标：可信交易与资金风控平台

> 文档状态：已确认的项目发展主线  
> 适用阶段：在保留现有二手交易能力的基础上持续演进  
> 说明：本文件定义目标与实施边界；现有“校园二手交易平台”PRD 仍作为当前功能基线保留。

## 一、项目主线

将 GreenLoop 从“校园二手交易平台”升级为：

**面向个人、组织与园区场景的可信资产交易平台，提供商品交易、模拟支付、资金托管、账户流水、退款结算、风险控制与后台运营能力。**

项目不再依赖“校园”身份或校园专属场地。初期仍聚焦闲置物品交易，以便复用已有商品、订单、聊天、配送、评价、管理端等能力；但领域模型、界面文案和规则设计应能支持个人用户、企业园区、机构内部资产流转等泛化场景。

本项目的核心价值不在于接入真实支付渠道，而在于完整、可信地模拟一笔交易从创建到结算或退款的业务闭环，并展示金融科技岗位关注的系统设计能力。

```text
商品发布与审核
        -> 下单与库存锁定
        -> 模拟支付与买方资金冻结
        -> 履约（发货 / 面交）
        -> 买方确认收货
        -> 卖方结算入账
        -> 评价、信用与运营分析

异常路径：取消、支付失败、超时关闭、退款、风控拦截、人工审核
```

## 二、目标业务范围

### 2.1 核心角色

| 角色 | 核心职责 |
| --- | --- |
| 买家 | 浏览商品、下单、充值模拟余额、支付、确认收货、申请退款、评价 |
| 卖家 | 发布商品、处理订单、履约发货或面交、接收结算款、查看资金流水 |
| 运营/风控人员 | 审核商品与用户、处理风险预警、介入争议订单、执行退款与冻结 |
| 系统管理员 | 管理角色权限、参数配置、审计记录和系统运行状态 |

### 2.2 资金交易闭环

资金能力采用“平台模拟账户”实现，不连接真实银行卡、第三方支付或清算机构，不存储真实敏感支付信息。

```text
买家模拟充值 -> 可用余额增加
买家支付订单 -> 可用余额减少、冻结余额增加
卖家履约       -> 等待确认收货
买家确认收货   -> 买家冻结余额减少、卖家可用余额增加
取消/退款      -> 买家冻结余额减少、买家可用余额恢复
```

每一次资金变化必须生成不可随意修改的流水记录，余额是流水计算结果在账户上的汇总表现。

### 2.3 明确边界

- 不接入真实支付、银行卡、征信、身份认证或真实金融清算网络。
- 不以“高并发秒杀”作为主线，优先保证资金账务的正确性、可追溯性与可恢复性。
- 不为了微服务而拆分微服务；先在当前架构中划清模块边界，复杂度确有必要时再拆分。
- 不删除或推翻既有校园交易功能；通过兼容迁移逐步泛化字段、文案和规则。

## 三、开发中必须守住的四个特性

这四项是项目区别于普通 CRUD 交易平台的关键，也是简历与面试中应重点讲清楚的部分。

### 3.1 一致性

同一笔订单、支付单、账户余额与资金流水必须保持一致，不能出现“扣了钱但订单未支付”“重复退款”“已结算后再次退款”等状态错乱。

- 使用明确的订单、支付、结算、退款状态机，只允许合法状态迁移。
- 余额更新、冻结/解冻、流水写入、业务单状态更新必须在同一数据库事务中完成。
- 对余额和库存采用乐观锁或条件更新，避免并发请求导致超扣。
- 金额统一使用 `BigDecimal` 或以分为单位的整数，禁止 `float`/`double`。
- 以订单号、支付单号和幂等键关联全链路业务记录。

### 3.2 幂等性

网络重试、重复点击和消息重复投递都可能发生；同一业务请求无论被执行一次还是多次，最终结果都必须相同。

- 支付、退款、确认收货、人工审核等关键接口必须携带并校验幂等键（如 `requestId`）。
- 服务端保存幂等请求的处理结果；重复请求直接返回首次结果，不重复扣款、入账或退款。
- 对异步补偿和定时任务同样设计去重机制。
- 对外暴露稳定的业务单号，避免仅依赖数据库自增 ID 作为请求幂等依据。

### 3.3 安全性

资金与账户数据属于高敏感业务数据，必须最小化暴露面，并把权限、输入、配置和操作风险控制在系统内。

- 采用 RBAC 权限模型，区分普通用户、运营人员、风控人员和系统管理员。
- 所有资金操作必须进行身份鉴权、资源归属校验和金额/状态校验。
- 密码、密钥、数据库口令、邮件授权码等不得写入仓库；使用环境变量或本地未提交配置。
- 对手机号、邮箱、身份证明类扩展字段进行脱敏展示，日志中不输出密码、令牌和完整敏感信息。
- 关键接口设置限流、重复提交防护和必要的异常告警。

### 3.4 可审计性

资金和风控决策必须能够回放：谁在何时因为什么执行了什么操作，操作前后发生了什么变化。

- 账户流水采用追加式记录，不允许物理删除或直接篡改历史金额。
- 记录关键操作审计日志：登录、支付、退款、冻结/解冻、审核、角色授权、后台人工干预。
- 审计记录至少包含操作者、角色、时间、关联业务单号、动作、结果、变更前后摘要与请求追踪号。
- 管理端支持按用户、订单、资金单号和时间范围检索，能够串联订单、支付、流水和审核轨迹。
- 审计日志与业务日志分层保存，避免普通日志清理后丢失关键证据。

## 四、目标模块与数据模型

### 4.1 新增或强化的领域模块

| 模块 | 目标能力 |
| --- | --- |
| 账户中心 | 用户资金账户、可用余额、冻结余额、余额变更版本号 |
| 充值与支付 | 模拟充值、支付单创建、支付确认、支付失败与超时关闭 |
| 资金账务 | 交易流水、冻结、解冻、结算、退款、冲正或补偿记录 |
| 订单中心 | 标准订单状态机、库存锁定、履约、确认收货、关闭与售后入口 |
| 清结算中心 | 卖方待结算金额、结算单、结算入账和结算异常处理 |
| 风控中心 | 用户/商品/交易风险规则、风险等级、拦截、人工审核和黑名单 |
| 审计与运营 | 操作审计、资金对账视图、异常订单处理、数据统计 |

### 4.2 建议核心表

| 表/实体 | 关键内容 |
| --- | --- |
| `account` | 账户主体、可用余额、冻结余额、账户状态、乐观锁版本 |
| `account_flow` | 流水号、账户、金额、方向、业务类型、前后余额、关联业务单号 |
| `recharge_order` | 模拟充值单、金额、状态、幂等键 |
| `payment_order` | 支付单、订单号、付款账户、金额、状态、支付请求号 |
| `settlement_order` | 结算单、收款账户、金额、状态、关联订单 |
| `refund_order` | 退款单、原支付单、退款金额、状态、退款请求号 |
| `account_freeze_record` | 冻结/解冻原因、金额、关联订单和状态 |
| `risk_record` | 风险对象、规则命中结果、风险等级、处置状态、审核意见 |
| `operation_audit_log` | 操作人、模块、动作、关联单号、前后摘要、追踪号、结果 |

金额字段统一采用 `DECIMAL(18,2)`；所有资金单据均需唯一业务单号、状态、创建时间、更新时间和关联订单号。核心资金流水需要保留变更前后余额快照，便于审计与对账。

## 五、分阶段落地顺序

### 阶段 0：基线梳理与项目重定位

目标：确定演进边界，让项目叙事、术语和架构方向一致。

- 将产品定位逐步调整为“可信交易与资金风控平台”。
- 梳理现有订单、商品、评价、配送、管理端能力及其与新主线的映射。
- 将“校园”“学生”“校内”等硬编码概念泛化为用户、区域、组织或交易地点；保留兼容字段和迁移方案。
- 先补齐统一错误码、参数校验、统一日志字段和 API 文档基础。

验收：能清楚演示已有交易流程，并说明它如何承接后续资金与风控模块。

### 阶段 1：订单状态机与库存一致性

目标：先让交易订单本身可靠，再引入资金。

- 定义订单状态、状态迁移条件、取消和超时规则。
- 引入商品库存锁定或在售状态的并发保护，避免同一商品被重复成交。
- 订单关键操作增加归属校验、重复操作拦截和操作记录。

验收：重复点击下单、取消、确认收货等操作不会产生不一致订单状态。

### 阶段 2：模拟账户、支付与资金流水

目标：完成“支付冻结 - 履约 - 结算/退款”的最小资金闭环。

- 创建账户、充值单、支付单、冻结记录和账户流水。
- 实现模拟充值、余额支付、余额冻结、确认收货结算、取消/退款解冻。
- 为支付、退款、结算接口实现幂等控制、数据库事务和并发保护。
- 在用户端提供余额、流水和订单资金状态查询；后台可查询资金单据。

验收：任意一笔完成、取消或退款订单均可通过订单、支付单和流水追溯其资金去向，且账户余额守恒。

### 阶段 3：风控、审核与运营处置

目标：让平台具备“风险识别 - 规则评估 - 自动阻断或转人工审核 - 运营处置 - 资金与业务联动 - 留痕复盘”的完整能力。阶段重点是建设规则可解释、决策可追踪、处置可闭环、资金可核对的基础风控平台，不以复杂机器学习模型为目标。

#### 风控原则

- 每次评估必须保存风险对象、业务场景、命中规则、实际指标、规则阈值、规则版本、风险等级、系统决策和最终处理结果，禁止只记录无法解释的风险分数。
- 系统决策统一为 `PASS`、`REVIEW`、`REJECT`，风险等级统一为 `LOW`、`MEDIUM`、`HIGH`、`CRITICAL`。
- 自动规则负责实时判断，人工审核负责处理中高风险事件；AI 仅用于商品合规、敏感文本和价格异常的辅助提示，不作为唯一拒绝依据。
- 风控处置不得绕过订单和资金状态机直接修改余额。审核拒绝必须通过退款、解冻和流水完成资金恢复。
- 人工放行、拒绝、加入黑名单和账户限制必须记录操作者、处理原因、时间、关联业务单号、状态变化和 `traceId`。

#### 风控对象与首批规则

- 用户风险：黑名单、短时高频下单或支付、频繁取消、连续创建超时订单、新用户立即进行大额交易、同一交易对手集中度异常。
- 商品风险：敏感词、违禁品、联系方式导流、疑似诈骗描述、价格明显偏离分类参考值、短时间批量发布相似商品。
- 交易风险：单笔金额过高、短时间交易次数或累计金额异常、风险用户或风险商品参与交易、商品价格与订单金额不一致。
- 资金风险：高频充值、充值后立即大额支付、频繁取消退款、支付/退款/结算金额不一致、账户余额与资金流水无法对平。
- 首批实现 `USER_BLACKLIST`、`SENSITIVE_PRODUCT_TEXT`、`ABNORMAL_PRODUCT_PRICE`、`HIGH_VALUE_TRANSACTION`、`HIGH_FREQUENCY_TRANSACTION`、`FREQUENT_CANCELLATION`、`RAPID_RECHARGE_AND_TRADE` 七类可解释规则。
- 规则阈值、风险等级、处置方式、启停状态和版本应支持后台配置；业务代码使用明确的规则处理器，不在本阶段建设通用脚本规则平台。

#### 业务接入与状态联动

- 商品发布前执行文本与价格风控：低风险商品正常上架，中风险商品进入 `PENDING_REVIEW`，明确违禁商品进入 `REJECTED`。
- 创建订单时检查黑名单、取消频率和交易频率。硬拦截规则命中时不创建订单、不锁定商品；首版对下单场景的 `REVIEW` 按暂时拒绝处理，避免引入额外订单中间态。
- 余额支付先执行黑名单等硬拦截规则；冻结成功后执行交易风险评估。低风险订单进入正常履约，中风险订单进入 `RISK_REVIEW`。
- `RISK_REVIEW` 期间商品保持 `LOCKED`、买家资金保持冻结，卖家不得发货，买家不得确认完成或自行取消。
- 人工放行后，订单根据配送方式进入 `AWAITING_MEETUP` 或 `AWAITING_SHIPMENT`。
- 人工拒绝后，在同一业务事务中解冻退款、取消订单、释放商品，并推进支付单、风险记录和审核记录状态；重复审核不得重复退款或重复推进订单。

#### 风险工作台与数据留痕

- 新增风险工作台，提供待审核队列、商品风险、交易风险、风险记录、黑名单和规则配置入口。
- 运营人员可查看命中规则、指标值、阈值、风险等级，以及关联用户、商品、订单、支付单、冻结记录和资金流水。
- 支持人工放行、人工拒绝、加入或移出黑名单、设置账户交易限制，并要求填写审核意见和幂等请求号。
- 建议新增 `risk_rule`、`risk_record`、`risk_review`、`risk_blacklist`；历史评估和审核记录不得物理删除，规则变化后仍需保留原规则版本与指标快照。
- 当前阶段可继续由 `ADMIN` 承担运营审核职责，运营、风控和系统管理员的细粒度 RBAC 拆分留到阶段 4。

#### 阶段边界

- 不实现完整退货、售后仲裁和逆向物流；退款仅作为风控拒绝后的资金处置手段。
- 不接入真实实名认证、银行卡、征信、IP 画像、设备指纹、地理位置或反洗钱系统。
- 不建设复杂机器学习模型和通用脚本规则引擎，不让 AI 独立作出封禁、拒绝交易或资金处置决定。

验收：能够稳定演示一笔异常大额交易在支付冻结后命中规则并进入 `RISK_REVIEW`，运营人员可查看完整命中依据并执行放行或拒绝；拒绝后资金只退款一次、订单取消、商品恢复可售，且风险记录、审核记录、订单、支付单和资金流水可以完整串联追溯。还需验证黑名单拦截、敏感商品审核、规则启停与版本快照、重复审核幂等和审核期间的操作限制。

### 阶段 4：安全、审计与工程化完善

目标：把可演示项目提升为可说明工程质量的项目。

- 完成 RBAC 权限细分、关键操作二次校验和后台操作审计。
- 清理仓库中的敏感配置，改为环境变量和示例配置文件。
- 引入数据库版本迁移工具（Flyway 或 Liquibase）、Docker Compose、本地一键启动说明。
- 增加关键服务单元测试与集成测试，重点覆盖支付幂等、余额变更、退款、状态机和权限。
- 增加 `traceId`、结构化日志、健康检查与关键异常监控指标。

验收：新环境可按文档启动；关键资金流程有自动化测试；异常请求可根据追踪号和审计记录定位。

## 六、优先级与取舍原则

1. 优先业务正确性：先做状态机、账户、流水、幂等和事务，再做页面美化与复杂推荐。
2. 优先可演示闭环：先实现模拟充值和余额支付，不等待真实支付接入。
3. 优先可解释设计：每个资金状态、风控结论和后台操作都要能解释原因、展示依据、回放过程。
4. 优先小步演进：复用现有单体项目和前后端结构；只有模块独立部署、容量隔离或团队协作确有需求时再服务化。

## 七、演示场景与最终验收

最终至少应可稳定演示以下场景：

1. 买家注册并模拟充值，卖家发布一件商品。
2. 买家下单并支付，系统校验余额后冻结相应资金，生成支付单和账户流水。
3. 卖家履约，买家确认收货，系统自动将冻结资金结算至卖家账户。
4. 买家在履约前取消或申请退款，系统将资金按规则退回并留存退款流水。
5. 对高风险用户或异常交易触发风控拦截，由运营人员审核并查看完整审计记录。
6. 对支付、退款、确认收货接口进行重复提交，验证资金不会重复变动。

## 八、简历与面试表达目标

项目完成后，可围绕以下表述组织简历与面试回答：

> 基于 Spring Boot、MySQL、Redis 与 Vue 3 设计并实现可信交易与资金风控平台，支持商品交易、模拟支付、资金托管、账户流水、退款结算、风险审核与后台运营。围绕支付幂等、交易状态机、余额并发更新、资金流水可追溯、RBAC 权限与操作审计等问题完成核心设计与实现，模拟银行清结算场景下的交易闭环。

面试准备应能结合代码具体说明：

- 一笔支付从请求进入到余额冻结、流水落库和订单更新的完整过程。
- 如何避免重复支付、重复退款与并发超扣。
- 为什么账务流水采用追加式记录，以及如何做订单与流水对账。
- 风控规则如何影响交易状态，人工审核如何留痕。
- 为什么当前选择模块化单体，以及未来如何按领域演进为独立服务。

## 九、后续执行约定

- 每次开发前，先确认改动属于哪个阶段、影响哪一条交易链路及是否触及四个核心特性。
- 涉及资金的需求必须同时设计：业务状态、账户变化、流水记录、幂等键、失败/补偿路径、权限与审计。
- 每完成一个阶段，补充对应接口文档、数据库迁移脚本、测试用例与演示步骤。
- 出现“快速绕过规则”的实现时，以一致性、安全性、可审计性和幂等性为最终裁决标准。
